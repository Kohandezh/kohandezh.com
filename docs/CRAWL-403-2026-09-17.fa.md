# چرا ElevenLabs (و هر خزندهٔ دیگری) سایت را نمی‌خزد — ۱۴۰۵/۰۶/۲۶

## یافتهٔ قطعی

`https://kohandezh.com/robots.txt` روی production **HTTP 403 Forbidden** برمی‌گرداند.

این مسئلهٔ ElevenLabs نیست. برای **همهٔ** user-agentها ۴۰۳ است:

| User-Agent | وضعیت robots.txt |
|---|---|
| `ElevenlabsBot/1.0` | **403** |
| `Googlebot/2.1` | **403** |
| `GPTBot/1.0` | **403** |
| Chrome (مرورگر معمولی) | **403** |
| بدون UA | **403** |

طبق RFC 9309، خزنده‌ای که برای robots.txt پاسخ 401/403 بگیرد مجاز است کل سایت را
«ممنوع» تلقی کند و بسیاری از خزنده‌های تجاری دقیقاً همین کار را می‌کنند. مستندات
ElevenLabs هم می‌گوید خزندهٔ آن robots.txt را رعایت می‌کند. بنابراین این یک علت
کافی برای شکست crawl است.

## دامنهٔ مشکل: ۱۵ فایل از ۱۶ فایل root

| فایل | وضعیت |
|---|---|
| robots.txt | **403** |
| llms.txt + ۹ نسخهٔ زبانی | **403** (هر ده تا) |
| feed.xml | **403** |
| manifest.json | **403** |
| sw.js | **403** |
| offline.html | **403** |
| sitemap.xml | 200 ✅ |

پیامدها فراتر از ElevenLabs است:
- **کل لایهٔ llms.txt در دسترس هیچ خزندهٔ هوش مصنوعی نیست** (GPTBot، ClaudeBot، PerplexityBot، ElevenLabs).
- **Service Worker روی production هرگز ثبت نمی‌شود** (`sw.js` = 403) — یعنی PWA و کش آفلاین مرده‌اند و نسخهٔ `CACHE_VERSION` بی‌اثر است.
- **manifest.json = 403** → نصب PWA کار نمی‌کند.
- **feed.xml = 403** → فید RSS در دسترس نیست.

## این چه چیزی **نیست**

بررسی‌های انجام‌شده این فرضیه‌ها را رد می‌کنند:

- **مسدودسازی بر اساس UA نیست** — همهٔ UAها ۴۰۳ می‌گیرند.
- **مسدودسازی جغرافیایی/IP نیست** — این تست‌ها از یک IP دیتاسنتر آمریکا
  (Ashburn, Virginia) اجرا شده‌اند و صفحات HTML سایت از همان‌جا ۲۰۰ می‌دهند
  (`/` و `/fa/` هر دو ۲۰۰، ~۲۲۷KB، TTFB ≈ ۱٫۹ ثانیه).
- **قانون مبتنی بر پسوند نیست** — فایل‌های ناموجود ۴۰۴ می‌دهند
  (`/definitely-not-here-xyz.txt` → 404)، فقط فایل‌های **موجود** ۴۰۳ می‌شوند.
  ضمناً `sitemap.xml` هم `.xml` است و ۲۰۰ می‌دهد ولی `feed.xml` ۴۰۳.
- **WAF یا Cloudflare نیست** — هیچ هدر CF وجود ندارد؛ پاسخ ۴۰۳ صفحهٔ خطای خود
  LiteSpeed است و هدرهای امنیتی سایت را هم حمل می‌کند، یعنی درخواست تا پیکربندی
  خود سایت پیش رفته است.

## علت محتمل (تأییدنشده — نیاز به دسترسی هاست)

الگو این است: فایل **روی دیسک هست** ولی وب‌سرور حاضر به سرو آن نیست. متداول‌ترین
دلیل این وضعیت **دسترسی (permission) یا مالکیت (ownership) اشتباه فایل‌ها** است —
دقیقاً چیزی که وقتی فایل‌ها با FTP یا File Manager با کاربر دیگری آپلود می‌شوند رخ
می‌دهد. `sitemap.xml` که درست کار می‌کند نشان می‌دهد سرو استاتیک از root فی‌نفسه
سالم است.

احتمال دوم: یک قانون `Require all denied` در `.htaccess` زندهٔ سرور. (`.htaccess`
زندهٔ production با نسخهٔ مخزن یکی نیست — ریدایرکت‌های قدیمی مخزن روی production
اعمال نمی‌شوند.)

از بیرون نمی‌توان بین این دو تفکیک قطعی داد.

## راه تشخیص و رفع (فقط مالک می‌تواند انجام دهد)

۱. در File Manager هاست، **permission و owner فایل `robots.txt` را با `sitemap.xml`
   مقایسه کنید**. `sitemap.xml` کار می‌کند؛ باید یکسان شوند.
۲. برای هر ۱۵ فایل `chmod 644` بگذارید و owner را با `sitemap.xml` یکی کنید.
۳. تست: `curl -I https://kohandezh.com/robots.txt` باید **200** و
   `content-type: text/plain` بدهد.
۴. اگر باز ۴۰۳ ماند، `.htaccess` ریشه را برای `Require all denied` /
   `<FilesMatch>` بررسی کنید.

### راه‌حل جایگزین و مقاوم‌تر برای ۱۱ فایل

وردپرس خودش `robots.txt` و هر ده فایل `llms.txt` را **به‌صورت داینامیک** سرو می‌کند:
- فیلتر `robots_txt` در `functions.php:652`
- قوانین rewrite در `functions.php:244` و `functions.php:248`

اما وردپرس فقط وقتی این کار را می‌کند که **فایل فیزیکی وجود نداشته باشد** (شرط
استاندارد `RewriteCond %{REQUEST_FILENAME} !-f`). یعنی همین الان فایل‌های فیزیکی
root دارند جلوی مکانیزم سالم وردپرس را می‌گیرند و خودشان ۴۰۳ می‌دهند.

اگر این ۱۱ فایل از root **حذف** شوند، وردپرس آن‌ها را با PHP و کد ۲۰۰ سرو می‌کند و
مشکل permission دیگر اصلاً موضوعیت ندارد. چهار فایل باقی‌مانده
(`sw.js`، `manifest.json`، `feed.xml`، `offline.html`) حتماً باید فایل استاتیک
بمانند و فقط با اصلاح permission درست می‌شوند.

> این تغییر در محتویات `root-files.zip` **اعمال نشده** است؛ تصمیم معماری با مالک است.

## آنچه هنوز نامشخص است

بدون متن خطای job در پنل ElevenLabs نمی‌توان گفت آیا ۴۰۳ تنها علت بوده یا علت‌های
دیگری هم هست. پس از رفع ۴۰۳، crawl باید دوباره اجرا شود و سند حاصل باید در تب
